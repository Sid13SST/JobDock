# JobDock design

Status markers: **[B1]** implemented in Batch 1, **[planned]** designed but not yet built.

## 1. Job state machine

```
            enqueue
               |
               v
   +------> QUEUED ----claim----> RUNNING ----success----> SUCCEEDED
   |                               |   |
   |   (backoff elapsed)           |   +--lease expired (worker crashed)--> QUEUED / FAILED_RETRY
   |                               |
   +--- FAILED_RETRY <--failure----+  (attempts < max_attempts)
                                   |
                                   +--failure, attempts >= max_attempts--> DEAD
```

| State          | Meaning                                                          | Built      |
|----------------|------------------------------------------------------------------|------------|
| `QUEUED`       | Waiting to run; eligible once `run_at <= now()`.                 | [B1]       |
| `RUNNING`      | Claimed by a worker (`locked_by`).                               | [B1]       |
| `SUCCEEDED`    | Handler returned normally. Terminal.                             | [B1]       |
| `FAILED_RETRY` | Last attempt failed; eligible again at `run_at` (backoff).       | [B2]       |
| `DEAD`         | Failed `max_attempts` times. Terminal; kept for inspection.      | [B2]       |

Terminal states are never left automatically.

## 2. Table schema

Batch 1 (`V1__create_jobs.sql`):

| Column            | Type          | Notes                                              |
|-------------------|---------------|----------------------------------------------------|
| `id`              | `uuid` PK     | generated by the application                        |
| `type`            | `text`        | selects the handler                                 |
| `payload`         | `jsonb`       | handler input                                       |
| `status`          | `text`        | CHECK in the five states above                      |
| `attempts`        | `int`         | incremented on every claim                          |
| `idempotency_key` | `text` NULL   | UNIQUE; NULL means "no dedup"                       |
| `run_at`          | `timestamptz` | not eligible before this time                       |
| `locked_by`       | `text` NULL   | worker id that holds the job while `RUNNING`       |
| `last_error`      | `text` NULL   | most recent failure (class: message), max 4000 chars; kept on DEAD and on a later success |
| `created_at`, `updated_at`, `started_at`, `finished_at` | `timestamptz` |              |

Batch 2 (`V2__add_max_attempts.sql`):

| Column         | Type  | Notes                                                                 |
|----------------|-------|-----------------------------------------------------------------------|
| `max_attempts` | `int` | total attempts allowed (first run included), CHECK 1..100; default 5 |

Batch 3 (`V3__add_lease.sql`):

| Column         | Type              | Notes                                                        |
|----------------|-------------------|--------------------------------------------------------------|
| `locked_until` | `timestamptz` NULL | lease expiry while `RUNNING`; CHECK set iff `status = 'RUNNING'` |

Index `jobs_running_lease_idx` on `(locked_until) WHERE status = 'RUNNING'` for the reaper.
Rows that were `RUNNING` when V3 ran get `locked_until = now()` (already expired), so
they are recovered.

Constraint `jobs_owner_iff_running`: `locked_by` is set if and only if `status = 'RUNNING'`.

Index: partial index on `(run_at, created_at)` `WHERE status IN ('QUEUED','FAILED_RETRY')`
so the claim query only scans claimable rows.

No separate `heartbeat_at` column: a heartbeat simply moves `locked_until`.

## 3. Enqueue and idempotency [B1]

`POST /jobs` with JSON body `{ "type": ..., "payload": {...}, "runAt": optional }`
and optional header `Idempotency-Key`.

```sql
INSERT INTO jobs (...) VALUES (...)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING ...
```

- Row returned -> new job, `201 Created`.
- No row (key already used) -> load the existing job by key:
  - same `type` and same `payload` (jsonb equality) -> `200 OK` with the original job;
  - different request -> `409 Conflict`. Reusing a key for a different request is a client bug.
- Concurrent requests with the same key: Postgres' unique index makes the second
  insert wait for the first transaction and then do nothing, so exactly one row is
  created. This is covered by an integration test.
- `runAt` and `maxAttempts` are not part of the replay comparison.
- Keys never expire in the current design (simple and honest; a TTL would be a later choice).

## 4. Claim protocol [B1]

```sql
WITH next AS (
  SELECT id FROM jobs
  WHERE status IN ('QUEUED', 'FAILED_RETRY') AND run_at <= now() AND type = ANY(:handled_types)
  ORDER BY run_at, created_at
  LIMIT :batch
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
SET status = 'RUNNING', locked_by = :worker, attempts = j.attempts + 1,
    started_at = now(), updated_at = now()
FROM next WHERE j.id = next.id
RETURNING j.*;
```

- One autocommit statement: row locks are held only while it runs.
- `SKIP LOCKED` makes concurrent workers skip rows another worker is claiming
  instead of blocking on them; each row is handed to at most one claimer.
- The locking CTE is evaluated once (avoids the known pitfall where a
  `WHERE id = (SELECT ... LIMIT 1)` subquery can be re-evaluated).
- A worker only claims types it has a registered handler for, so a job of an
  unknown type stays `QUEUED` (visible, runnable once a handler is deployed)
  instead of being claimed and stuck.
- Ordering is best-effort FIFO by `run_at`; strict ordering is **not** guaranteed
  (skipped locked rows and parallel workers reorder completion).

Completion:

```sql
UPDATE jobs SET status='SUCCEEDED', locked_by=NULL, locked_until=NULL, finished_at=now(), updated_at=now()
WHERE id = :id AND status = 'RUNNING' AND locked_by = :worker AND attempts = :attempt
```

**Fencing [B3]:** every transition out of `RUNNING` (success, failure, heartbeat)
names the claim it belongs to: `(locked_by, attempts)`. `attempts` is
incremented by every claim, so it works as a fencing token: once a job has been
reclaimed, the previous claim's updates match 0 rows — even if the same worker
id got the job back for a later attempt. 0 rows is logged and never treated as
success.

The handler runs between claim and completion with no transaction open.

Worker process [B1]: `WorkerPool` starts `jobdock.worker.threads` threads, each a
`Worker` with its own id (`<host>-<pid>-<random>-<n>`), polling with
`batch-size` and sleeping `idle-delay` when nothing was claimed or a poll failed.
On shutdown it stops claiming and waits up to `shutdown-timeout` for in-flight
jobs. Correctness does not depend on the pool: two threads or two processes are
kept apart by the claim statement alone.

## 5. Lease and heartbeat

**Lease [B3].** The claim sets `locked_until = now() + lease` (`jobdock.worker.lease-duration`,
default 30s; database clock). A `RUNNING` job always has a lease (CHECK constraint).

**Heartbeat [B3].** Each worker tracks the claims it holds and has not finished —
the running job *and* the not-yet-started rest of its claimed batch — as
`job id -> attempt`. One heartbeat thread per `WorkerPool` runs every
`lease / 3` and, per worker, extends all of them in one statement:

```sql
UPDATE jobs j SET locked_until = now() + :lease
FROM unnest(:ids, :attempts) AS c(id, attempt)
WHERE j.id = c.id AND j.attempts = c.attempt AND j.status = 'RUNNING' AND j.locked_by = :worker
RETURNING j.id
```

A held claim that is not returned is **lost** (it was reclaimed). If that job has
not started yet, the worker skips it. If it is already running, the handler is
*not* interrupted; it runs to the end and its result is rejected by fencing
(section 4). Heartbeat errors are logged; the leases then simply expire.
During graceful shutdown heartbeats continue until in-flight jobs finish.

## 5a. Lease reaper [B3]

Every `WorkerPool` runs a reaper thread every `jobdock.worker.reaper-interval`
(default 5s). It takes back `RUNNING` jobs whose lease expired, in batches of 100:

```sql
WITH expired AS (
  SELECT id, locked_by FROM jobs
  WHERE status = 'RUNNING' AND locked_until < now()
  ORDER BY locked_until LIMIT :limit
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j SET
  status      = CASE WHEN j.attempts >= j.max_attempts THEN 'DEAD' ELSE 'FAILED_RETRY' END,
  run_at      = CASE WHEN j.attempts >= j.max_attempts THEN j.run_at ELSE now() END,
  finished_at = CASE WHEN j.attempts >= j.max_attempts THEN now() END,
  last_error  = 'Lease expired: worker <id> stopped heartbeating during attempt <n>',
  locked_by = NULL, locked_until = NULL, updated_at = now()
FROM expired WHERE j.id = expired.id
```

- **Concurrent reapers** (several instances): `SKIP LOCKED` skips rows another
  reaper holds; a row changed and committed by another reaper, heartbeat or
  completion before we lock it is re-checked under the lock and no longer
  matches. Each expired job is requeued once (tested with 8 concurrent reapers).
- **Reaper vs. late completion / heartbeat:** both are single-row `UPDATE`s on the
  same row; whichever commits first wins and the other matches 0 rows (fencing).
- The abandoned attempt counts toward `max_attempts`, so a job that crashes its
  worker every time ("poison pill") ends `DEAD` instead of looping forever.
- A reaped job is due immediately (no backoff): the usual cause is a dead worker,
  not the job. Trade-off: a poison pill is retried quickly, up to `max_attempts`.
- A lease can only expire if heartbeats stop for a whole lease period: worker
  process dead, heartbeat thread starved, or the worker cut off from the database.

## 6. Retry and backoff [B2]

On handler failure (any `Throwable` thrown by `handle`), with `n = attempts`
(already incremented by the claim):

```
if n >= max_attempts: status = DEAD          (run_at unchanged, finished_at = now())
else:                 status = FAILED_RETRY, run_at = now() + delay(n)
delay(n) = min(base * 2^(n-1), max_delay) * (0.5 + 0.5 r),   r uniform in [0, 1)
```

- One `UPDATE ... WHERE id = :id AND status = 'RUNNING' AND locked_by = :worker`;
  the DEAD-or-retry decision is made in SQL from the row's own `attempts` and
  `max_attempts`, so it cannot race with another writer. 0 rows -> the worker no
  longer owns the job; logged, nothing changed.
- `run_at` uses the database clock (`now()`), like the claim's `run_at <= now()`
  check, so app/DB clock skew cannot make a retry early or late. Only `delay(n)`
  is computed in Java (`BackoffPolicy`, randomness injected for tests).
- `owner` is released and `last_error` set in both cases.
- Defaults: `jobdock.retry.base-delay` 1s, `jobdock.retry.max-delay` 5m,
  `max_attempts` 5 per job (1..100, settable on enqueue). With these defaults a
  job is attempted 5 times, with retries roughly 0.5–1s, 1–2s, 2–4s and 4–8s after
  each failure (plus poll latency), then dead-lettered.
- Jitter factor in [0.5, 1.0) spreads retries of jobs that failed together.
- The claim picks `FAILED_RETRY` rows exactly like `QUEUED` rows once
  `run_at <= now()`, with the same `SKIP LOCKED` protocol.
- A job of an unregistered type cannot normally be claimed; if it ever is, it is
  recorded as a failed attempt rather than stranded.
- Any `Throwable` from a handler is a failed attempt [B3], including `Error`s
  such as `StackOverflowError` or `AssertionError`. After an `OutOfMemoryError`
  the JVM may be unusable; if the failure cannot be recorded, lease expiry
  recovers the job.
- If writing a result (success or failure) throws, e.g. the database is
  unreachable, the worker logs it and continues with the rest of its batch [B3].
  That job is no longer heartbeated, so its lease expires and the reaper requeues
  it; the handler runs again. On an interrupt (shutdown timeout) the worker stops
  starting further jobs of its batch; those leases expire the same way.

## 7. Delivery semantics (honest statement)

**At-least-once.** A job is run at least once unless it is dead-lettered, and it
may run more than once. Concretely, a handler can run again if:
- the worker crashes after the handler's side effects but before the completion
  `UPDATE` commits;
- (once leases exist) a handler outlives its lease (e.g. a long GC pause or a
  network partition from the DB) and the job is reclaimed.

Therefore **handlers must be idempotent** (e.g. use the job id as a dedup key
for side effects). What the queue does guarantee:
- a job is never handed to two workers by the claim protocol at the same time
  while its claim is valid (tested: N workers x M jobs, each job executed once on
  the success path);
- a committed enqueue is never lost (it is a durable Postgres row);
- a failed attempt is retried with backoff until `max_attempts`, then kept as
  `DEAD` with its `last_error` [B2] — a retry is a new attempt, so a handler that
  failed *after* a side effect will repeat it;
- a crashed worker's jobs are eventually retried [planned, lease recovery].

"Exactly once" is not claimed.

## 8. Failure scenarios

| # | Scenario | Expected behaviour | Status |
|---|----------|--------------------|--------|
| 1 | Many workers poll at the same time | Disjoint sets of jobs (SKIP LOCKED); each job's handler runs once on the success path | [B1] tested: 8 workers x 1000 jobs; 2 pools x 4 threads with 4 concurrent producers x 250 jobs |
| 2 | Same idempotency key sent twice (sequential or concurrent) | One job; replay returns it | [B1] tested |
| 3 | Same key, different body | 409, no new job | [B1] tested |
| 4 | Job scheduled in the future | Not claimed before `run_at` | [B1] tested |
| 5 | Completion by a worker that doesn't own the job | 0 rows, not marked succeeded | [B1] tested |
| 6 | API process crashes after enqueue commit | Job persists (Postgres durability) | by design |
| 7 | Handler throws | `FAILED_RETRY`, `run_at = now() + delay(attempts)`, `last_error` set; retried when due | [B2] tested |
| 8 | Handler fails `max_attempts` times | `DEAD`, `last_error` of the last attempt kept, never claimed again | [B2] tested |
| 8a | Retrying jobs under contention | A job in retry is held by at most one worker at a time; each attempt number runs once | [B2] tested: 2 pools x 4 threads, 300 jobs failing twice then succeeding + 100 jobs dead after 3 attempts |
| 9 | Worker process killed mid-job | Lease expires, job requeued, runs again | [planned] |
| 10 | Worker stalls past lease, then completes | Completion rejected (not owner) | [planned] |
| 11 | No handler registered for `type` | Not claimed; stays `QUEUED` | [B1] tested |
| 12 | Database unavailable | Poll loop logs and backs off; no state lost | [planned] |
